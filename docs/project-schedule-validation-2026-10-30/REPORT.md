## Reproduced problem

Project Settings accepted a target of 4 November while its non-deleted task was due 5 November at 11:59 PM (+08:00). The metadata workflow validated the project's own start/end order and past-date rules, but did not compare the project interval with task schedules. Readiness made the same omission.

## Fix

- The database rejects project dates that exclude existing task starts or due dates, naming a conflicting task and date. Equal boundary dates are valid.
- Task creation, scheduling, linking and restoration are checked against the project's current bounds. Existing RPCs and direct table writes reach the same triggers.
- Date-only values and timestamp deadlines are compared as Manila calendar days. Due-date fallback works when no measurable deadline exists. Unresolved relative schedules remain planning values.
- Non-deleted scheduled tasks constrain the project regardless of work status. Soft-deleted tasks are excluded; restoration rechecks their schedule.
- Setup readiness shows the conflict and disables activation. The server also prevents activation/completion of an existing invalid schedule.
- Existing dates are not changed. Unrelated metadata edits remain possible for legacy records. Users resolve the conflict by extending the project or rescheduling the task.
- Settings retains rejected drafts, displays the server's explanation, avoids a success message and does not repeat the rejected save. Its timeline help describes the containment rule.

The integrity functions are private, use fixed search paths and reuse the existing project serialization key. Trigger-only definer visibility prevents collaborating-Office RLS from hiding a conflicting task without granting clients broader reads or callable helper endpoints. The installed readiness wrapper retains its baseline review, staffing, Office identity and lifecycle checks.
