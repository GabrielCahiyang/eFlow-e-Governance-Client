# Phase 17 — owned release gates

The registry is a conservative, source-linked **call-site inventory**, not certification of every current service. It includes reads, draft helpers, callbacks, preferences and operation wrappers. Each candidate has an action ID and an owned `S17-<feature>` gate. A gate blocks a new safety/authority/audit release claim for that caller; it does not disable an existing supported workflow or silently authorize a missing operation.

## Evidence requirements

To close a candidate gate, inspect its navigation entry and callers, prove the effective role/capability/RLS/RPC path, classify its actual risk, and attach cancellation, duplicate, stale, draft, outcome/retry and audit evidence appropriate to that action. Mark an absent capability as unsupported instead of building a client workaround. `safety:check` fails when source fingerprints or generated coverage change or a new caller lacks an owned disposition. `safety:update` explicitly records new unresolved callers; review its diff. Merely running the generator does not verify a gate.

The TypeScript AST scanner includes named functions, imported operations, JSX callbacks, keyboard/blur callers, persistence methods and operation wrappers. Relative imports are followed through public re-exports. Gateway Python writes are conservatively indexed from call text. SQL evidence links the latest matching migration function body, its fingerprint, visible guard expressions and direct audit/ledger inserts. Dynamic dispatch, unusual verbs, delegated SQL calls, triggers, function overloads and live deployment need manual review. Stable IDs tolerate line movement; repeated identical calls use an ordinal and source fingerprints detect changed files.

## Receipt limitations and rollback

Phase 17 converted actions reject duplicates synchronously and hold saved or uncertain action versions for the mounted context. Refresh failure never triggers a second write. There is no persisted request registry: remount/reload clears these client safeguards. Independently check the canonical record/history before retrying an uncertain operation. A successful write plus a successful explicit read can allow a deliberate repeat only for supported repeatable actions such as pause/resume or template copying; this is not automatic retry.

Roll back each caller adapter independently, with its regression test. Preserve existing server operations and protections, source inventory, gate ownership and evidence. Do not relax policy to make a confirmation test pass.
