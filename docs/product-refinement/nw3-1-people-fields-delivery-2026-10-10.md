## Behavior and integration contract

These standalone components do no reads/writes and infer no roles. Each field receives explicit `leadId`, `contributorIds`, authorized current `people`, its distinct fresh NW2 adapter result, `busy`, and controlled `onChange`. The future owner must recalculate `appointmentCapability` from **appoint_lead** and `contributorCapability` from **manage_contributors** for the current root/node scope each render. Missing/denied/inconsistent availability disables changes; contributor permission does not enable appointment. Busy/revoked state retains displayed values. Controls use native labelled form elements, stable `useId` labels/reasons and `type="button"` add/remove actions, without invitation actions or service imports.

Pass original worker IDs as `contributorIds` even where the storage array includes the current Lead. Display always deduplicates and excludes explicit Lead from chips/count/add/remove. The appointment callback is `onChange(nextLeadId, retainedContributorIds)` and retains the supplied original worker list (deduplicated, order preserved), without silently removing an old Lead or adding an appointment-only historical Lead. It does not serialize or write a command. At a worker-array command boundary, `compatibilityWorkWorkerIds(nextLeadId, retainedContributorIds)` includes the new Lead exactly once while keeping original workers. Example: Lead A/workers `[A,C]` → Lead B/compatibility workers `[A,C,B]`; Lead A/workers `[C]` → Lead B/workers `[C,B]`. Explicit later removal is a separate callback, subject to the future owner's current server/impact checks. Do not use this helper to fabricate personal root worker payloads.

Only `eligible === true` directory entries are selectable. Unknown eligibility is denied; duplicate conflicting eligibility is denied; approved guests are accepted only when the scoped server directory marks them eligible, without client home-Office filtering. Historical/ineligible people stay named in summaries/chips/current Lead options, with a missing-name fallback. A historical Lead option is disabled for selection. Lead is never inferred from the first worker; null remains needs-reassignment. An ineligible retained roster is not silently fixed by these fields: mutation eligibility and any conflicting transfer remain server-controlled.

Existing visible screens, sidebar/navigation, staffing dialogs, workflows, public APIs and service return values are unchanged. Branch authority, Office boundaries, selected/guest membership/expiry, evidence security, finance, hierarchy/depth/revisions and historical authorship are preserved. The confirmed Office rule remains **own eligible Subitem Lead first, then eligible parent/ancestor Leads, Task Lead and responsible Head; skip the submitter**. The recorded current parent-first SQL discrepancy remains deferred to NW4.1; no reviewer SQL was changed or claimed corrected. Official root Head and personal independent review remain separate and unchanged.
