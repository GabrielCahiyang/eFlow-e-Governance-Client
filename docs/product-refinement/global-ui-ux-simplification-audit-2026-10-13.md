## 1. Decision rules and audit limits

**One primary navigation context, one authoritative navigation system, and local workflow/filter controls only inside their destination.** Keep useRoleNavigationState, navigationUrl, navigationHistory and navigationGuard as the existing route/transition owner. Do not introduce competing activePrimary, category or queue stores.

There are three different control levels:

1. Primary/context navigation chooses the main destination: My Work, Reviews, Office Budget, Settlements or an Admin support tool. Its general destination selector appears once in the active layout.
2. A local workflow/view selector chooses content inside that destination: Reviews kind or Office Budget view. It uses the same accepted URL/history path and appears once locally; it is not duplicated in the sidebar.
3. Local filters constrain the current authorized data: search, sort, date, workspace filter, fiscal year, record state and History recent-completed. Preserve useful filters, defaults and visible active-filter state.

For example, keep the local review-kind selector and queue search/sort; replace Budget’s two area/leaf selector layers with one compact local view control. Remove Accounting’s page-wide Overview/Releases/Settlements/Journal/History/Budget bar because those destinations already exist in its context rail. A record’s evidence/journal/membership link and an Inspector’s local tabs remain legitimate contextual interactions.

Removed means removing a redundant control/wrapper, not deleting a business component, route, service, data or history. Merged shares presentation/ownership, never decision authority. Relocated preserves an existing function at a clearer location. Redesigned reduces clutter while retaining contracts. Preserved keeps an intentional distinction. Already implemented items are preservation/regression work only.

This is a source/document refresh. GitHub metadata was read and fetched; current source and checked-in tests were inspected. No application tests, hosted database reads, actor sessions, new screenshots, mutations, migrations or deployments were performed for this revision. Existing test coverage is a verification target, not a new passing CI or live-acceptance claim.

No database/API change is proposed. The only future hosted target remains ixnfphgjyelhckjwjkdv, with live migration timestamps preserved. A missing backend capability requires separate diagnosis/review and cannot be smuggled into this presentation plan.

## 3. Final proposed navigation architecture

**Retain the existing route owner.** useRoleNavigationState reads navigationUrl and synchronizes accepted URL/history transitions; EflowAppShell performs guarded selection and current-actor/generation checks. navigationHistory and navigationGuard remain the shared event/guard path. Extend those contracts narrowly for validated workflow queries instead of adding another router or active-navigation store.

Existing roleNavigation/sidebarContent, administrativePages and ACCOUNTING_VIEWS remain authoritative source registries. A derived presentation adapter may annotate groups/labels/query schemas, but must not duplicate role permissions, supported destination lists or defaults. Desktop rail, mobile drawer, fallback and search consume those same records.

Flow: **current URL + current access → existing route state → primary group/context destination → content → one local workflow selector plus useful data filters**. Accepted preference restoration is subordinate to the URL and fresh authorization. Record Inspector state and secure notification intents remain feature-owned.
