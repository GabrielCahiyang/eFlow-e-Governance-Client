## Explicit account-isolation decision

Before making dependent account-draft changes, asked the user to resolve NW8's destructive clear-on-account-change against NW9.4 draft preservation. The user explicitly chose per-account draft isolation: hide the previous actor's draft and evidence immediately, retain unsaved feedback privately, and recover only after fresh authorization for the same pending submission/review target and version with appropriate review capability. Never transfer feedback between actors or attempts; never restore old evidence/submission snapshots. Invalid or denied drafts stay inaccessible. Reviewer routing, authority, historical decisions and submission ownership must remain unchanged.

Implemented a runtime-memory feedback vault keyed by actor ID, review context kind, Task ID, Subitem ID, submission ID and version. It stores only feedback and local edit order. It contains no evidence, submission snapshots, names or credentials. Actor/sign-in changes remount visible state immediately; the old actor's asynchronous callbacks cannot publish state/toasts into the new actor's UI. Fresh queue/capability verification supplies all restored display/evidence data. Different versions, closed attempts, access denial and readOnly capability never restore or silently submit the old draft. Quarantined feedback remains private in memory. Explicit discard, manually clearing feedback or a confirmed successful decision removes only that actor/target draft. Navigation/remounts and actor changes do not delete it. This memory-only lifetime does not promise recovery after a full page/process restart; no browser-persistent sensitive feedback is added.

Decision dispatch optionally validates the originating actor against the current session, then pins that request's Authorization header to the originating session token. A session switch cannot send actor A's private feedback as actor B. This is a client freshness guard, not a new authority rule: the server still validates the JWT/current reviewer and all financial gates. The old three-argument API and RPC payload/void result remain compatible. No token is stored or logged. The Supabase skill was applied earlier in this conversation; checked the installed PostgREST builder and official [setHeader reference](https://supabase.com/docs/reference/javascript/using-modifiers-setheader) for the request-local override. No global client/account configuration changes.
